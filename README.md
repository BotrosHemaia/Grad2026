# Graduation Party — Seat Reservation System

## Project Overview
- **Name**: grad-party-seating
- **Goal**: Let event staff ("servants") reserve and track seats for a graduation party in real time — from an initial "Available" state through "Pending", "Confirmed", or "Blocked".
- **Stack**: React 18 + TypeScript (Vite) on the frontend, **Firebase Firestore** as the sole backend/database. No custom server — the browser talks to Firestore directly via the Firebase SDK.

> **Status of this task**: Backend data layer, models, and Firebase wiring are complete. **The UI itself has intentionally not been built yet** — pages currently render a bare, unstyled list to prove the Firestore connection works end-to-end. Building the real seat-map / reservation UI is the next step.

## Data Architecture

### Firestore Collections

**`seats`**
| Field | Type | Notes |
|---|---|---|
| `id` | string (doc ID) | auto-generated by Firestore |
| `seat_number` | string | e.g. `"A1"` |
| `status` | `'Available' \| 'Pending' \| 'Confirmed' \| 'Blocked'` | |
| `reservation_id` | string \| null | back-reference to the owning reservation, kept in sync by the service layer |

**`reservations`**
| Field | Type | Notes |
|---|---|---|
| `id` | string (doc ID) | auto-generated by Firestore |
| `guest_name` | string | |
| `phone_number` | string | |
| `payment_method` | `'Cash' \| 'InstaPay'` | |
| `servant_name` | string | staff member who registered the booking |
| `seat_ids` | string[] | seat document IDs included in this reservation |
| `created_at` | Firestore server timestamp | set automatically on creation |

Type definitions live in `src/types/models.ts`.

### Why a transaction-based service layer?
Booking a seat touches **two** collections at once (mark seat `Pending`/`Confirmed` **and** write the reservation). `src/services/reservationService.ts` wraps these writes in Firestore `runTransaction` calls so:
- Two servants can never double-book the same seat (the transaction re-checks each seat's status before committing).
- Cancelling a reservation always releases its seats back to `Available` atomically.

## Setup Guide

### 1. Create a Firebase project
1. Go to the [Firebase Console](https://console.firebase.google.com/) → **Add project**.
2. Enable **Firestore Database** (start in test mode, or production mode + use `firestore.rules` here).
3. In **Project Settings → General → Your apps**, register a **Web app** and copy the config values.

### 2. Configure environment variables
```bash
cp .env.example .env.local
# then fill in VITE_FIREBASE_API_KEY, VITE_FIREBASE_PROJECT_ID, etc.
```
`.env.local` is git-ignored — never commit real Firebase keys (note: Firebase web API keys are not secret in the traditional sense, but Firestore access is still governed by `firestore.rules`, which you should tighten before going live).

### 3. Install & run locally
```bash
npm install
npm run dev        # Vite dev server on http://localhost:5173 (or use dev:sandbox for port 3000)
```

### 4. Seed initial seats
Edit `scripts/seedSeats.mjs` (`ROWS`, `SEATS_PER_ROW`) to match your venue, then:
```bash
npm run seed:seats
```
This bulk-creates `seats` documents all set to `Available`. It refuses to run if the collection is already non-empty (to avoid duplicates).

### 5. Deploy Firestore rules/indexes (optional, requires Firebase CLI)
```bash
npx firebase deploy --only firestore:rules,firestore:indexes
```

## Deployment (Frontend)
This is a static SPA — build output can be hosted anywhere static (Cloudflare Pages, Firebase Hosting, Netlify, etc.):
```bash
npm run build       # outputs to dist/
npm run deploy       # deploys dist/ to Cloudflare Pages (project: grad-party-seating)
```
Remember to set the same `VITE_FIREBASE_*` variables in your hosting provider's build environment.
